# Observability and Monitoring Requirements

## 1. Core Principles (The Three Pillars)

| ID           | Requirement               | Tooling / Technology | Rationale                                                                                                               |
| :----------- | :------------------------ | :------------------- | :---------------------------------------------------------------------------------------------------------------------- |
| **OBS-P-01** | **Comprehensive Logging** | Fluentd/Loki         | All services must generate structured logs to facilitate easy searching and analysis.                                   |
| **OBS-P-02** | **System Metrics**        | Prometheus/Grafana   | All services must expose standard and custom metrics for real-time performance monitoring and alerting.                 |
| **OBS-P-03** | **Distributed Tracing**   | Jaeger               | A mechanism must be in place to track the full lifecycle of a request across all microservices to identify bottlenecks. |

---

## 2. Distributed Tracing Requirements

Tracing is mandatory for understanding performance and failures in the microservices architecture.

| ID           | Requirement                      | Constraint / Detail                                                                                                                      |
| :----------- | :------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| **OBS-T-01** | **Trace ID Generation (Source)** | A unique **Trace ID** must be generated at the absolute entry point of the application—either the frontend (Next.js) or the API Gateway. |
| **OBS-T-02** | **ID Propagation**               | The Trace ID **MUST** be propagated downstream via HTTP headers in every single request between microservices (Golang services).         |
| **OBS-T-03** | **ID Logging Correlation**       | Every log line generated by any microservice (Golang) **MUST** include the active Trace ID and Span ID for complete correlation.         |
| **OBS-T-04** | **Data Capture**                 | Spans must capture essential information, including service name, operation name, start/end time, latency, and status code.              |

---

## 3. Metrics Requirements (Prometheus & Grafana)

All services must expose operational and business metrics for proactive monitoring and alerting.

| ID           | Requirement                  | Metric Type / Detail                                                                                                                                                                               |
| :----------- | :--------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OBS-M-01** | **Standard Service Metrics** | All Golang services must expose standard metrics, including CPU utilization, memory usage, request rates, error rates, and latency (P50, P95, P99).                                                |
| **OBS-M-02** | **Business Metrics (API)**   | Critical business transactions (e.g., `User_Login_Success`, `Product_View_Count`, `Coupon_Applied_Attempt`) must be tracked as custom metrics.                                                     |
| **OBS-M-03** | **Alerting**                 | Alerts **MUST** be configured in Prometheus/Grafana for critical failures, including high error rates (e.g., 5xx errors > 5%), high latency (P95 > 500ms), and near-capacity resource utilization. |
| **OBS-M-04** | **Database Metrics**         | Database usage (PostgreSQL, MongoDB, Redis) **MUST** be monitored, including active connections, query execution time, cache hit ratios, and replication lag.                                      |

---

## 4. Logging Requirements (Loki)

Logging must be structured and actionable, supporting rapid debugging.

| ID           | Requirement                       | Constraint / Detail                                                                                                                                      |
| :----------- | :-------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OBS-L-01** | **Structured Logging**            | All logs **MUST** be generated in a structured format (e.g., JSON) to ensure fields (timestamp, level, service, trace_id) are easily queryable.          |
| **OBS-L-02** | **Security & Compliance Logging** | All critical security events (logins, authorization failures, data updates) **MUST** be logged at the `WARN` or `ERROR` level for easy auditing.         |
| **OBS-L-03** | **Log Retention**                 | Application logs **MUST** be retained for a minimum of **30 days** for debugging, and security/audit logs for a minimum of **6 months**.                 |
| **OBS-L-04** | **Error Context**                 | All error logs **MUST** include sufficient context, including the function name, line number, relevant input parameters, and the full error stack trace. |
